1. Purpose

This document defines the database model and API contract for the Minor
Project.

It translates the approved project architecture and functional
requirements into an implementation-level specification that can be used
while developing the backend, DynamoDB tables, API Gateway routes, and
React frontend.

This document is subordinate to the project master specification and
architecture document. If a future change conflicts with those
documents, the change must be explicitly reviewed before implementation.

2. Scope

The Minor Project contains four logical DynamoDB entities:

Users

Incidents

Ambulances

Hospitals

The backend exposes application APIs through:

React → API Gateway → Lambda → DynamoDB

The Resource Allocation Engine runs inside the backend Lambda layer.

The Minor does not require a third-party mapping, routing, or geocoding
API.

3. General Data Conventions

3.1 Identifier Format

Every entity uses a unique identifier.

Recommended implementation:

UUID-style string

Generated by the backend

Never supplied as a trusted identifier by the client when creating a
new record

Examples:

userId: usr_...
incidentId: inc_...
ambulanceId: amb_...
hospitalId: hsp_...

The exact UUID library/format may be finalized during implementation.

3.2 Timestamps

All timestamps should be stored as ISO 8601 strings in UTC.

Example:

2026-09-04T07:30:00Z

Fields:

createdAt

updatedAt

The backend should generate authoritative timestamps rather than
trusting arbitrary client timestamps.

3.3 Coordinates

Locations use:

latitude
longitude

Recommended validation ranges:

latitude: -90 to 90
longitude: -180 to 180

The Minor uses these coordinates for approximate geographical distance
calculations.

3.4 Lists

Fields such as equipment, facilities, and required resources are
represented as arrays of strings.

Example:

["OXYGEN", "DEFIBRILLATOR"]

Exact allowed values should be controlled by backend validation.

8. DynamoDB Table Strategy

The Minor uses separate logical DynamoDB tables/entities:

Users
Incidents
Ambulances
Hospitals

We intentionally do not use DynamoDB single-table design for the initial
Minor implementation.

This keeps the data model easier for a beginner developer to understand,
implement, test, document, and explain during viva.

Each entity is connected through IDs.

Example:

Incident.assignedAmbulanceId
        ↓
Ambulances.ambulanceId

and:

Incident.assignedHospitalId
        ↓
Hospitals.hospitalId

No SQL-style joins are required.

All application APIs are exposed through Amazon API Gateway and
implemented by AWS Lambda.

General flow:

React
  ↓
API Gateway
  ↓
Lambda
  ↓
DynamoDB

The Lambda layer is responsible for:

business rules

response formatting

error handling

The React frontend must not directly access DynamoDB.

14. Allocation API

14.1 POST /incidents/{id}/allocate

Purpose

Runs the Resource Allocation Engine for an incident.

This is one of the most important Minor Project APIs.

Request

No body is required for the initial design.

POST /incidents/{id}/allocate

Backend Processing

The allocation engine should:

Load the incident.

Confirm the incident exists.

Confirm it is eligible for allocation.

Retrieve ambulance candidates.

Remove BUSY and OFFLINE ambulances.

Check required equipment.

Calculate approximate geographical distance.

Calculate an explainable ambulance suitability score.

Select the best ambulance.

Retrieve hospital candidates.

Remove inactive hospitals.

Check capacity.

Check required facilities.

Calculate geographical distance.

Calculate an explainable hospital suitability score.

Select the best hospital.

Persist the assignment.

Set ambulance status to BUSY.

Set ambulance assignedIncidentId.

Set incident assigned resource IDs.

Update incident status.

Return allocation details.

The exact scoring formula is intentionally not frozen in this document.
It must be designed and tested before implementation.

Important Consistency Requirement

Allocation should avoid inconsistent partial updates.

Where possible, DynamoDB transactional operations should be considered
when multiple records must change together.

For the initial implementation, the developer must explicitly handle
failures so that a failed allocation does not silently leave an
ambulance marked BUSY without a corresponding incident assignment.

Success Response

Recommended shape:

{
  "message": "Resources allocated successfully",
  "allocation": {
    "incidentId": "inc_example",
    "ambulance": {
      "ambulanceId": "amb_example",
      "distanceKm": 3.42,
      "score": 91.5
    },
    "hospital": {
      "hospitalId": "hsp_example",
      "distanceKm": 5.18,
      "score": 87.0
    }
  },
  "incidentStatus": "ALLOCATED"
}

The returned score and distance are explanatory results of the
allocation decision. They do not need to be permanently stored in the
incident record unless a later requirement justifies storing an
allocation/audit record.

20. Distance Calculation Contract

The Minor does not call a third-party mapping service.

Lambda calculates approximate geographical distance using the stored
latitude and longitude.

The recommended method is the Haversine formula.

Conceptually:

incident coordinates
        +
ambulance coordinates
        ↓
Haversine calculation
        ↓
approximate distance in kilometres

The same approach can be used for hospital distance.

This distance is calculated at allocation time and does not need to be
stored permanently.

Important limitation:

Straight-line geographical distance is not road distance or travel
time.

A future Major extension may introduce a routing service if realistic
road distance/ETA provides sufficient value.

21. Allocation Engine Contract

The allocation engine must be deterministic and explainable for the same
input state.

It must not randomly select a resource.

The conceptual contract is:

Input:
    incident
    available ambulances
    active hospitals

Output:
    selected ambulance
    selected hospital
    ambulance suitability explanation
    hospital suitability explanation

Selection factors include:

Ambulance

availability

equipment match

geographical distance

other approved suitability factors

Hospital

operational status

bed capacity

facility match

geographical distance

other approved suitability factors

The exact weighting formula will be documented separately when the
allocation implementation begins.

22. Concurrency and Consistency Considerations

A resource may be requested by more than one allocation operation.

The implementation must avoid a simple unsafe sequence such as:

read ambulance
→ see AVAILABLE
→ allocate

without considering that another request may have changed the ambulance
between the read and write.

The implementation should use conditional writes and/or DynamoDB
transactional operations where appropriate.

At minimum:

an ambulance should only transition to BUSY if it is still
AVAILABLE

the incident should only be assigned after successful resource
reservation

failed allocation should not silently leave resources reserved

This is particularly important because resource allocation is the core
technical feature of the project.

23. API Security Requirements

The backend must:

authenticate protected requests

authorize actions by role

validate all client input

never trust frontend-only role checks

avoid exposing password hashes

avoid exposing internal errors

avoid hardcoded secrets

use HTTPS through the AWS API layer

apply least-privilege IAM permissions to Lambda

The frontend should not contain:

AWS access keys
AWS secret keys
database credentials
third-party API secrets

24. DynamoDB Security

Lambda should access DynamoDB using an IAM execution role.

The frontend should never connect directly to DynamoDB using AWS
credentials.

Permissions should be limited to the tables/actions actually required by
each backend function.

The project should avoid broad permissions such as unrestricted access
to all DynamoDB resources unless temporarily necessary during controlled
development.

32. Change Control

The following are considered architectural/API contract changes and
should be discussed before implementation:

adding/removing a core entity

changing an existing endpoint

changing required fields

changing status values

changing role definitions

changing the allocation engine's core purpose

replacing DynamoDB with another database

adding a third-party API

introducing additional AWS services into the Minor

Minor implementation details may be changed when required for
correctness, security, or maintainability.
